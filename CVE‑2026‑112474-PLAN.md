# Plan for CVE‑2026‑112474 (IOHIDEvent UAF)

## Overview
The goal is to get a user‑land binary that can trigger the **use‑after‑free** in the IOKit HID subsystem on a physical Apple Watch Series 9 running watchOS 27.0.1.  The exploit lives in a **private** part of the `IOHIDEvent` API – the public SDK exposes only the interface.  The plan describes the steps you need to take to recover that private header, reverse‑engineer the struct layout, build a helper binary, deploy it to the device, and observe the kernel crash with LLDB.

---

## 1. Locate the private IOKit header

`xcrun` can find the path of a tool or header.  The header that contains the vulnerable struct is normally under the WatchOS SDK directory.

```bash
xcrun --sdk watchos --find /usr/include/IOKit/IOHIDLib.h
```

If that returns a path, copy the file to a working directory.

## 2. Inspect the struct layout

Open the header (e.g. with `less` or `vim`) and look for `struct IOHIDEvent`.  The private API will include a comment `// **DO NOT USE**` or similar.

- **Field of interest**: the pointer that points to the internal buffer (likely called `buf` or `data`).
- Note the offset of that field – this is the offset the kernel uses to read the buffer.

## 3. Verify kernel symbol table

You need to know where the kernel function that handles the event lives.  Use `lldb` to inspect the device’s symbol table.

```bash
xcrun --device 00008310-000D73DC0108A01E lldb
lldb> image list
```

Find the module that contains the IOKit handler; note its address.  You can also use `lldb> disassemble` to see the instruction that dereferences the buffer.

## 4. Build the PoC helper binary

Create a C file that includes the private header, creates an event, corrupts the buffer, and sends it to a dummy HID device.  Compile for the watch architecture (arm64‑t8010) and link against IOKit.

```bash
mkdir -p build
cp /Library/Developer/Platforms/WatchOS.platform/Developer/SDK/WatchOS.sdk/usr/include/IOKit/hid/IOHIDLib.h build/

clang -target arm64-apple-watchos-27.0 -O0 -g -I./build \
  -F/Library/Developer/Platforms/WatchOS.platform/Developer/SDK/WatchOS.sdk/usr/lib \
  -framework IOKit PoC_CVE-2026-112474.c -o build/poC.dylib
```

## 5. Deploy and run on the device

Use `xcrun` to run the binary directly on the connected watch.

```bash
xcrun --device 00008310-000D73DC0108A01E ./build/poC.dylib
```

If the binary starts, the kernel will process the event and (hopefully) crash.

## 6. Observe the crash with LLDB

Attach `lldb` to the device again and set a breakpoint in the kernel function you identified in step 3.  When the PoC runs, the breakpoint will hit and LLDB will show the crash stack.

```bash
xcrun --device 00008310-000D73DC0108A01E lldb
lldb> breakpoint set -n IOHIDEventSetProperty
lldb> run
```

When the kernel panics, LLDB’s backtrace will reveal the exact address the kernel tried to read – this confirms the UAF.

## 7. Iterate if necessary

If you do not get a crash:

- Double‑check the UDID of the device.
- Verify you are building for the correct target (`watchos` SDK).
- Inspect the kernel symbol table again – the function name may differ.
- Adjust the corruption offset (e.g. overwrite a different byte in the buffer).  The vulnerability is sensitive to the layout.

## Final checklist before you run

1. **Confirm device is connected** – `xcrun devicectl list devices` should list the Watch as *connected*.
2. **Make sure you have the full SDK** – `xcrun --show-sdk-version` should report `watchos27.0`.
3. **Copy the private header** – if you don’t see it, try `xcrun --find /usr/include/IOKit/IOHIDLib.h` or look under `/Library/Developer/Platforms/WatchOS.platform/Developer/SDK/WatchOS.sdk/usr/include/IOKit`.
4. **Verify the UDID** – run `xcrun devicectl list devices` and copy the exact UDID string.
5. **Compile the PoC** – run the script, watch for compile errors.
6. **Run the PoC** – the script will launch it; if the kernel crashes, you’ve hit the flaw.

> **If the PoC does not crash**
> • The kernel may have been patched for 27.0.1.
> • You might need to adjust the buffer corruption (e.g., overwrite a different byte or the pointer field).
> • Use `lldb` to inspect the event pointer inside the kernel at the breakpoint and confirm the offset matches the header.
